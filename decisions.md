# Architecture & Technology Decisions

Every choice documented with reasoning and justification.

## Day 3: FastAPI Base
1. **Packaging**: We chose `uv` workspace structure over plain pip / poetry because dependency resolution and virtual environments are significantly faster (< 1s vs 30s+).
2. **Environment & Secrets Validation**: We chose strictly required environment fields without hardcoded defaults for `SECRET_KEY` (minimum 32 characters required) and `DATABASE_URL` (must use an async scheme like `postgresql+asyncpg://`). `ENVIRONMENT` is constrained to `Literal["development", "staging", "production", "testing"]`. Any invalid or missing configuration immediately raises a `ValidationError` at startup.
3. **Password Hashing**: We chose `pwdlib[argon2]` over `bcrypt`/`passlib` because `passlib` has been unmaintained since 2020 and fails on Python 3.14 due to missing `crypt` module.
4. **Database Driver**: We chose `asyncpg` + `SQLAlchemy 2.0 (async)` over synchronous drivers because FastAPI is an async ASGI framework and non-blocking I/O is critical for concurrency.
5. **Deduplication Strategy**: We chose SHA-256 content hashing with a composite unique index on `(tenant_id, content_hash)` over document-level filename checks so re-uploading identical content is detected regardless of the filename.
6. **Multi-Tenancy Model**: We chose a shared-database, shared-schema architecture with a strict `tenant_id` column enforced at the repository/dependency layer because it provides clean resource sharing with minimal operational complexity at early stage.
7. **Transactions are committed in services**: services own `commit()` and handle `IntegrityError` for races (same email or same file at once). The session dependency only opens and closes the session, because its exit code runs after the response is sent.
8. **Error envelope**: every error is `{"error": {"code", "message", "request_id", "details?"}}`. Application errors are `AppError` subclasses with a stable `code`; Starlette HTTP errors, validation errors and unexpected exceptions go through the same shape. Unexpected errors never leak their message.
9. **Document hash covers the raw bytes**: SHA-256 of the uploaded file, so the same file is detected whatever its name, and a changed PDF is a different document. Uniqueness is per tenant `(tenant_id, content_hash)`.
10. **Lists never include `content`**: `DocumentResponse` is a summary, `DocumentDetail` adds the text. A page of 100 documents cannot return gigabytes.
11. **Uploads are read in 1 MB chunks** and rejected with 413 as soon as the total passes the limit; PDF parsing runs in `asyncio.to_thread` because `pypdf` blocks.
12. **Two login endpoints**: `POST /auth/login` takes JSON, `POST /auth/token` takes the OAuth2 password form so Swagger's Authorize button works. Both use the same service.
13. **Token tenant must match the user's tenant**: `get_current_user` loads the user and rejects the token when its `tenant_id` claim differs from the database, so a claim cannot be swapped. `decode_access_token` also requires `exp`, `iat`, `sub` and `tenant_id`.
14. **The stream demo requires authentication**, like every future AI endpoint will.
15. **`email-validator`** was added for `EmailStr`; `CORS_ORIGINS` is optional and adds the CORS middleware only when set.

## Day 5: LLM integration (chat, streaming, structured output)
16. **One SDK for both models**: the `openai` SDK talks to Gemini (hosted) and Ollama (local) because both copy the OpenAI chat-completions protocol (Day 4). A request picks one with `backend: "hosted" | "local"`. Routes depend on a small `LLMProvider` protocol, so tests use a fake and never touch the network or a key.
17. **Providers are optional at start-up**: the service starts without `LLM_API_KEY`; only the hosted backend answers `503 LLM_NOT_CONFIGURED`. One client per backend is built on first use and closed in the lifespan.
18. **`conversations` and `messages` carry `tenant_id` (and conversations `user_id`)**: every query filters on tenant and user, and another tenant's or user's conversation is a 404, like documents. Message ids are an increasing integer, so "oldest first" is exact even when two rows share a timestamp.
19. **The history sent to the model is the last `CHAT_HISTORY_LIMIT` stored messages** (default 20) plus a system prompt that is never stored. The cap keeps cost and latency flat (Day 4 task 5); summarising old messages is a later step.
20. **Nothing is stored until the model has produced its first event**: `POST /chat` waits for the first event, and only then saves the conversation and the user message and starts answering. A provider that is down is a plain `502` and leaves no half-finished rows.
21. **The reply is saved by the stream itself**, in a session of its own (`get_session_factory`), because the request's session is gone by the time the stream ends. Its status says how it ended: `complete`, `cancelled` (client left, partial text kept) or `error` (provider failed mid-way, partial text kept). An empty reply is not saved.
22. **Errors in the middle of a stream are SSE events** (`event: error` with a generic message), because the `200` status line is already sent. Details go to the log only.
23. **`/extract` uses native structured output**: the JSON Schema comes from the Pydantic model (`Enquiry.model_json_schema()`), every field is required but may be `null` / `"unknown"` (the model is told never to guess), and the reply is validated with `model_validate_json`. One retry shows the model its own validation error; then `422 EXTRACTION_FAILED`. A reply cut off by the token limit is not retried.
24. **The text to extract is passed inside `<message>` tags** and the system prompt says it is data, not instructions (prompt-injection hygiene; there is a sample for it in the comparison script).

## Day 6: reliability, cost and provider abstraction

25. **One `LLMClient` protocol with `generate`, `stream`, `generate_structured`** (`services/llm_types.py`). Routes and services use only my own types (`LLMRequest`, `LLMResponse`, `Usage`, `StreamEvent`, my error classes); the two SDKs are imported in `llm_openai.py` and `llm_anthropic.py` only. The Day 5 names `stream_chat` and `complete_json` are gone.
26. **Adapters: OpenAI-compatible (Gemini, Ollama) and Anthropic.** `OllamaProvider` is a thin subclass that only sets the backend name. Anthropic has no JSON-schema switch here, so structured output forces a tool whose input schema is mine (tool-as-schema). The Anthropic adapter is tested against a fake server only: there is no Anthropic key in this project.
27. **Usage is normalised in the adapter.** `Usage.input_tokens` is new input only; cached input is `cache_read_tokens`, cache writes are `cache_write_tokens`. OpenAI style puts the cached part inside `prompt_tokens` (subtracted in the adapter), Anthropic reports it apart. Unknown usage stays `None`, never 0.
28. **My own error types decide retry and fallback**, not HTTP codes in the callers: `retryable` (429, 5xx, 529, timeout, connection) and `fallback_ok` (those, plus an exhausted daily quota). A bad key, a bad request, a context that is too long and a refusal are raised at once. A 429 with "per day" or `insufficient_quota` in it is a quota error, not a rate limit, so it is not retried.
29. **Layers that are themselves clients**: `Fallback( Retrying( Limited( Accounting( adapter ) ) ) )`. Accounting is closest to the provider, so every real call (each retry, each fallback) is its own log line and `llm_calls` row. The SDKs' own retries are off (`max_retries=0`); with both on, 3 x 3 calls would happen.
30. **Retry = exponential back-off with full jitter, `retry-after` obeyed, and a total time budget** (`LLM_RETRY_*`). A stream is only retried or moved to the fallback **before the first text**; after that the client has seen words and an `error` event is the only honest answer. The wrappers prime a stream up to its first non-start event for exactly this reason.
31. **Cost = tokens x a price table in the settings** (`LLM_PRICES`, USD per million; override with JSON). A model with no price is logged with `cost = null`. The Gemini free tier does not bill, so its cost is "what the paid tier would charge". Money is `Decimal` in the code and `NUMERIC(14,8)` in the table.
32. **`llm_calls` has one row per provider call**, with `tenant_id`, `user_id`, `feature`, tokens, `cost_usd`, latency and status. Foreign keys are `SET NULL`, so the cost history survives deleting a user or a tenant. Saving the row can fail without failing the request (it is logged).
33. **Concurrency is limited per backend** with a semaphore (`LLM_MAX_CONCURRENCY`) and, for `hosted`, a sliding-window calls-per-minute limiter (`LLM_REQUESTS_PER_MINUTE`, 0 = off). Limits sit inside the retry layer so that every attempt counts against them.
34. **`/extract` repairs at most twice** (3 tries in all). Each repair prompt keeps the whole conversation, so the model sees all its earlier mistakes. A refusal (`content_filter`) is its own handled error, `422 EXTRACTION_REFUSED`, and is never retried; a cut-off reply is never retried either.
35. **Prompt caching for `/chat`** (Day 7: the file is now the registry prompt `chat_system` v1, see 44): the system prompt is read from a file (`CHAT_SYSTEM_PROMPT_FILE`), is the first thing in every request and never changes; history follows, the new message is last. Anthropic gets `cache_control` on the system block; Gemini and OpenAI cache a long prefix by themselves, so there is nothing to mark. The hit is read from `usage` and shown in the `done` event and the log.
36. **Blank values in `.env` mean "not set"** (`LLM_API_KEY=`, `ANTHROPIC_API_KEY=`, `LLM_FALLBACK_BACKEND=`): found when `.env.example` copied as it was made `SecretStr("")` count as a configured key.
37. **`Enquiry` has sanity checks the JSON schema cannot express** (phone of 8 to 15 digits, a real-looking email, a budget between 0 and 10,000,000, a name or city of at most 60 characters). They are plain Pydantic validators, not schema keywords, so every provider accepts the schema; a failing check starts the repair loop. Without them no repair ever ran, because strict schema mode makes every answer valid in shape. They catch absurd values (phone `python`, a budget of 5 x 10^15), not believable invented ones.
38. **Routes give back their database connection before calling the model** (`await session.commit()` after authentication): a request that holds a connection while it waits for a slow model empties the pool under load (25 at once gave ten 500s).

## Day 7: prompt registry and the classifier prompt

39. **Prompts are files in a registry**: `prompts/<name>/<version>.md`, loaded by `get_prompt(name, version)` (`services/prompt_registry.py`). The name and version are checked against a pattern before they touch the file system (no path can leave `prompts/`), a missing prompt raises `PromptNotFoundError`, loaded prompts are cached, and Jinja2 `StrictUndefined` turns a missing variable into an error. A new version is a new file; an old one is never edited.
40. **Every model call records which prompt made it**: `CallContext` carries `prompt_name` and `prompt_version` into the JSON log line and two new nullable columns of `llm_calls` (migration `0a123456546c`). When a call uses several prompt files (`/extract` uses a system, a user and a repair prompt) the system prompt's name and version are the ones recorded, and the three files change version together.
41. **All `/extract` prompts moved into the registry** (`extract_system`, `extract_user`, `extract_repair`, all `v1`, text identical to the old strings; checked character by character). The chat prompt files were not changed.
42. **Classifier prompt: `classify_query` v2 is kept.** Measured on 30 labelled cases (two runs, identical answers, `gemini-3.1-flash-lite`, hosted):

    | Version | What it is | Accuracy (hard set, both runs) | Accuracy (independent easy set) | Cost per 1,000 calls | Output tokens |
    |---|---|---|---|---|---|
    | v1 | zero-shot | 26/30 (86.7%) | 29/30 | 0.018 USD | 4 |
    | **v2** | structure, definitions, rules | **30/30** | **30/30** | **0.086 USD** | 1 |
    | v3 | v2 + 6 examples | 30/30 | 29/30 | 0.112 USD (+30%) | 1 |
    | v4 | v3 + reasoning | 30/30 | 29/30 | 0.174 USD (+103%) | 22 |

    v1 is the cheapest by far but 13.3 points behind on the hard set, followed an injected instruction ("say hello in French") and put its answer in free text in 17 to 19 of 30 replies, so it fails the "within 2 points" rule. Examples (v3) and chain-of-thought (v4) added cost and **no accuracy**: v2 is the cheapest version within 2 points of the best on both sets.
43. **Limits of that decision (said openly):** the hard set was written together with the v2 rules, so its 100% is optimistic; the independent easy set (written separately, before the v2 rules) supports it but is easy. One case is 3.3 points on 30 cases, so "within 2 points" means "equal to the best". Two category definitions had to be made to agree with the labels first ("when does the next batch start" is `schedule`; a problem that already happened is `complaint` even when the topic is fees). Labels of the arguable cases (for example "I cancelled my registration yesterday. When will my refund be processed?" is `fees` in the easy set; v3 and v4 said `complaint`) need a human decision. Only one model and one run configuration were tested.
44. **The chat prompts are in the registry too** (Day 7, task 2 finished): `prompts/chat_system/v1.md` (the long handbook, moved with `git mv`, identical text) and `prompts/chat_basic/v1.md` (the one-line default). The settings `CHAT_SYSTEM_PROMPT` and `CHAT_SYSTEM_PROMPT_FILE` are replaced by `CHAT_PROMPT_NAME` (default `chat_basic`) and `CHAT_PROMPT_VERSION` (default `v1`); `chat_service.chat_prompt()` loads it and the route records its name and version on the call context. Checked live on the Docker database: three `/chat` turns on `chat_system` v1 saved `prompt_name = chat_system`, `prompt_version = v1`, and turns 2 and 3 read 2,030 and 2,027 tokens from the cache, as on Day 6. A stale `CHAT_SYSTEM_PROMPT_FILE` in an old `.env` is now ignored silently (the settings ignore unknown keys), so the server falls back to the one-line prompt: change it to `CHAT_PROMPT_NAME=chat_system`. Every prompt in the project is now a registry file.
